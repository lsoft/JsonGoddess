# Что взять у System.Text.Json

Разбор исходников `dotnet/runtime` (MIT), сентябрь 2026, ветка `main`. Смотрел не «как у них красиво»,
а две вещи: **какие приёмы применимы у нас** и **где проходит граница между тем, что они вынуждены
делать в рантайме, и тем, что мы делаем на этапе компиляции**. Вторая половина важнее: она и есть
ответ на вопрос, откуда берётся выигрыш.

Файлы, на которые ссылаюсь:

| Файл | Про что |
|---|---|
| `Serialization/Metadata/PropertyRef.cs` | упаковка имени свойства в `ulong`-ключ |
| `Serialization/Metadata/JsonTypeInfo.Cache.cs` | поиск свойства по UTF-8-имени в рантайме |
| `Reader/JsonReaderHelper.net8.cs`, `.netstandard.cs` | векторизованный скан строки, и его скалярный дубль |
| `Reader/JsonReaderHelper.Unescaping.cs` | разворачивание escape-последовательностей |
| `Writer/JsonWriterHelper.Escaping.cs` | поиск первого экранируемого символа |
| `Writer/JsonWriterHelper.Date.cs`, `JsonHelpers.Date.cs` | лексика даты в обе стороны |
| `JsonConstants.cs` | пороги и максимальные длины |

## 1. Где мы структурно дешевле — поиск свойства

Это главное наблюдение, и оно подтверждает гипотезу из плана числом и кодом сразу.

**Что делают они.** Имя свойства, прочитанное из документа, надо сопоставить с членом типа. Готовой
таблицы «имя → член», известной компилятору, у них нет и быть не может: `JsonTypeInfo` строится в
рантайме. Поэтому `GetProperty` работает в три ступени:

1. посчитать `ulong`-ключ из имени и линейно пройти **кэш** `PropertyRef[]`, сравнивая ключи;
2. промах — раскодировать имя **в UTF-16** и посмотреть в основной словарь;
3. положить результат в кэш, если тот не дорос до `PropertyRefCacheBuilder.MaxCapacity`.

То есть на каждое свойство каждого объекта — вычисление ключа, проход по кэшу, а на холодных и на
вытесненных именах ещё и транскодирование плюс словарь.

**Что делаем мы.** Ключ вычисляется так же (иначе никак — имя приезжает из документа), но дальше
стоит `switch` по константам, известным генератору. Ни кэша, ни словаря, ни UTF-16, ни промахов.
Это не «мы написали быстрее», это разные объёмы работы.

**Что отсюда забираем — упаковку ключа.** Раскладка у них такая: старший байт — длина имени, младшие
семь — первые семь байт имени. Следствие, которое стоит проговорить: **для имени длиной до 7 байт
ключ полон**, то есть совпадение ключа доказывает совпадение имени, и `SequenceEqual` не нужен
вовсе. Для имён длиннее — префильтр, и сравнение остаётся.

**Замер (A/B внутри одного прогона) показал, что «лучше» здесь не безусловное.** На форме, где длины
имён разводят члены по разным корзинам, `switch` по длине попадает в член сразу, и ключ становится
чистым расходом; на форме, где все имена одной длины, ключ выигрывает крупно:

| | switch по длине | switch по ключу | |
|---|---:|---:|---|
| REGULAR (7 членов, длины разные) | **573.6 ± 29 ns** | 651.3 ± 23 ns | ключ на 13.5% хуже |
| WIDE (30 членов, все по 7 байт) | 817.7 ± 39 ns | **587.2 ± 16 ns** | ключ на 28% лучше |

Интервалы не перекрываются ни в одну сторону. Вывод для эмиттера — не «брать ключ», а «выбирать
форму по набору имён»; подробности в [PLAN.md](../PLAN.md) §8.2. Приём берём, безусловность — нет.

Сама форма switch'а по ключу выглядит так:

```csharp
switch (JsonNameKey.Compute(name))
{
    case 0x07_30_30_64_6C_65_69_46UL:   // "Field00", 7 байт - ключ полон
        ...                              //   сравнение не нужно
        break;

    case 0x09_65_63_6E_65_72_65_66UL:   // "Reference", 9 байт - только префильтр
        if (!name.SequenceEqual("Reference"u8)) { goto unknown; }
        ...
        break;
}
```

**Мина, которой у них нет, а у нас есть: порядок байтов.** Они считают ключ в рантайме через
`BitConverter`, поэтому обе стороны сравнения всегда на одной машине. У нас константа печатается
генератором на **сборочной** машине, а сравнивается на **целевой**. Значит и печатать, и читать
обязательно с явно заданным порядком — `BinaryPrimitives.ReadUInt64LittleEndian`, а не
`BitConverter.ToUInt64`. На практике big-endian .NET почти не существует, но «почти» здесь стоит
одной строчки.

Проверять это будет форма WIDE: там все тридцать имён по семь байт, то есть ровно случай, когда
сравнение исчезает целиком.

## 2. Векторизованный скан — берём в обе стороны

**Чтение.** У них один вызов ищет сразу **кавычку, обратный слэш и любой управляющий символ**:
`SearchValues<byte>` из 34 значений (0x00–0x1F, `"`, `\`) и `IndexOfAny`. Один проход находит и конец
строки, и необходимость разэкранирования, и нарушение RFC 8259 §7.

У нас сейчас `IndexOfAny(Quote, Backslash)` — двухзначная перегрузка, тоже векторизованная, но
управляющие символы она не видит.

Следствие для конструкции, а не только для скорости: **страж `ControlCharsInStrings` становится почти
бесплатным**, потому что скан всё равно идёт. В плане (§6.3) он записан как opt-in с собственной
ценой; если замер покажет, что 34-значный `SearchValues` не дороже двухзначного `IndexOfAny`, страж
надо делать безусловным — это ровно судьба `QuotedAttributes` в XmlSerDe. Решается замером, не
рассуждением.

**Запись.** У них `IndexOfAnyExcept(s_allowedBytes)` по списку **разрешённых** символов. Нюанс,
который стоит знать при чтении наших же бенчмарков: этот быстрый путь работает только для энкодера
по умолчанию; с `UnsafeRelaxedJsonEscaping` — с тем самым, чей набор мы повторяем, — они уходят в
виртуальный `encoder.FindFirstCharacterToEncodeUtf8`. Наш бенчмарк меряет STJ с опциями по умолчанию,
то есть **на их быстром пути**; сравнение в этом месте консервативно в их пользу.

У нас `JsonStringEncoder.IndexOfEscapable` — скалярный цикл по символам. Наш набор экранируемого
(`"`, `\`, всё ниже 0x20) — это 34 значения, все ниже 0x80, то есть `SearchValues<char>` уложит их в
ASCII-битмап. Один векторизованный `IndexOfAny` вместо цикла. Список пишем **запрещённый**, а не
разрешённый: у нас он маленький и не зависит от опций.

Это, похоже, самый дешёвый крупный выигрыш из всего списка — на строковых полезных нагрузках.

На netstandard2.0 `SearchValues` нет; там остаётся скалярный цикл. У них ровно то же деление на
`.net8.cs` и `.netstandard.cs`, и это подтверждает, что наш `#if`-подход не самодеятельность.

## 3. Разэкранирование — берём массовое копирование между escape'ами

Их цикл между двумя escape-последовательностями делает `IndexOf('\\')` и копирует весь кусок разом,
а не по символу.

У нас `JsonStringDecoder.Unescape` идёт посимвольно всегда. На строке с одним `\n` в середине это
значит посимвольный проход по всей строке вместо двух `CopyTo`. Чинится в несколько строк.

**Чего у них берём наоборот — ничего.** Они разэкранируют **в байтах**, а потом транскодируют; мы
транскодируем, а потом разэкранируем **в символах**. Их порядок заставляет собирать суррогатную пару
руками (`Rune`, сложение старшего и младшего суррогата, кодирование в UTF-8); у нас `😀`
даёт два `char`, которые сами по себе и есть пара. Наш код короче и, судя по тому, что вся
escape-матрица уже совпадает с BCL, не менее правильный. Порядок не меняем.

## 4. Лексика даты — половину уже взяли, вторую половину стоит

**Запись.** Они форматируют `Utf8Formatter`'ом с `'O'` и потом срезают хвостовые нули дробной части
вместе с осиротевшей точкой. Наш `JsonValueFormatter.TrimFraction` делает то же самое — совпадение
не случайное, а потому что паритетный тест не оставил выбора: STJ пишет `2020-01-02T03:04:05`, а не
`...05.0000000`.

**Чтение.** Здесь они сильно впереди: `JsonHelpers.Date.cs` — свой разборщик ISO 8601 прямо по
байтам, со структурой `DateTimeParseData` на стеке, проверкой цифр арифметикой (`b - (uint)'0'`) и
без единой строки. У нас — транскодирование в стековый буфер символов и `DateTime.TryParse`, а на
netstandard2.0 ещё и `ToString()`, то есть аллокация на каждую дату.

Свой байтовый разборщик — отложенная работа, но теперь у неё есть доказательство целесообразности:
команда, которая может позволить себе всё, написала его руками вместо вызова BCL. В плане это
кандидат в оптимизации после первого профиля документа с датами.

## 5. Константы — сверка

| Их | Значение | Наше | Вывод |
|---|---|---|---|
| `MaxExpansionFactorWhileEscaping` | 6 | `JsonStringEncoder.MaxBytesPerEscape` = 6 | совпало |
| `MaximumFormatInt64Length` | 20 | `MaxIntegerBytes` = 24 | запас есть |
| `MaximumFormatDecimalLength` | 31 | `MaxRealBytes` = 40 | запас есть |
| `MaximumFormatDoubleLength` | 128 | `MaxRealBytes` = 40 | у них запас под произвольный формат; у нас формат один, 40 хватает (`-1.7976931348623157E+308` — 24) |
| `MaximumFormatDateTimeOffsetLength` | 33 | `MaxDateTimeBytes` = 40 | с кавычками 35, запас есть |
| `MaximumFormatGuidLength` | 36 | `MaxGuidBytes` = 40 | с кавычками 38 |
| `Delimiters` = `",}] \n\r\t/"` | — | нет | см. ниже |

**`Delimiters`** — у них после числа или литерала обязан стоять разделитель, иначе документ отвергается
(`1abc` не проходит). У нас `ReadNumberRaw` просто остановится, а `1abc` уедет в `Utf8Parser` целиком
и не разберётся — то есть отказ будет, но по другой причине и с другим сообщением. Это материал для
`JsonGuard.StrictNumbers`, а не отдельная задача.

## Что делать, по убыванию отношения выигрыша к цене

1. **`SearchValues<char>` в `IndexOfEscapable`** (net8+, скаляр в `#else`). Самый дешёвый крупный
   выигрыш на записи строк.
2. **Массовое копирование между escape'ами** в `JsonStringDecoder.Unescape`. Несколько строк.
3. **`ulong`-ключ вместо switch по длине** в диспетчере имён — это уже решение по форме
   генерируемого кода (§8.2 плана переписать). Обязательно `BinaryPrimitives` с явным порядком байтов.
4. **`SearchValues<byte>` в `ReadStringContent`**: один скан вместо двухзначного `IndexOfAny`, и
   страж управляющих символов достаётся даром. Сперва замерить — 34 значения против двух не обязаны
   быть быстрее.
5. **Свой байтовый разборщик ISO 8601** — отложить до профиля, но запланировать.

Пункты 1 и 2 не меняют наблюдаемого поведения, поэтому их страхует уже написанная паритетная матрица:
если после правки хоть одна строка корпуса разъедется с BCL — тест покраснеет.
